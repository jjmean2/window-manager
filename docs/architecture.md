# 동작 원리

창 관리자가 안에서 어떻게 동작하는지 설명합니다. 코드를 고치거나 다른 디자인 시스템으로 옮길 사람을 위한 문서입니다. 쓰는 방법은 [사용 가이드](./guide.md)에, 왜 이렇게 만들었는지는 [결정 기록](./decisions.md)에 있습니다.

## 모듈 구성

`packages/window-manager/src` 아래에 있습니다. React 와 무관한 모듈이 계산과 상태를 맡고, React 파트는 그것을 DOM 에 연결하기만 합니다. 단위 테스트는 React 와 무관한 모듈에만 있습니다.

| 모듈 | 맡은 일 | React | 테스트 |
|---|---|---|---|
| `geometry.ts` | 이동 제약(`clampPosition`, `containPosition`), 리사이즈 계산(`resizeRect`) | 무관 | 27개 |
| `placement.ts` | 배치에서 실제 자리를 구함(`effectiveRect`), 스냅 대상 판정(`snapTargetAt`), 끌어서 풀기(`detachRect`) | 무관 | 19개 |
| `gesture.ts` | 누름 하나에서 시작된 제스처의 수명(`createPointerSession`) | 무관 | 11개 |
| `events.ts` | 관리자별 누름 표시, 타이틀바 안의 인터랙티브 요소 판별 | 무관 | 3개 |
| `store.ts` | 창 목록·순서·활성 창·배치를 갖는 상태 저장소 | 무관 | 52개 |
| `context.ts` | 저장소를 내려 주는 컨텍스트, 값 하나를 골라 구독하는 hook | 사용 | 없음 |
| `WindowManager.tsx` | `Root`, `Viewport`, `Area`, `SnapPreview`, `useWindowManager`, `useWindowList` | 사용 | 없음 |
| `Window.tsx` | 창 파트 8개, `useWindow`, 제스처를 DOM 이벤트에 연결하는 hook | 사용 | 없음 |

## 상태 모델

관리자 하나(`WindowManager.Root`)가 저장소 하나를 갖습니다.

```ts
interface WindowManagerState {
  layout: WindowLayout          // 저장·복원 대상
  activeId: string | null       // 활성 창
  openIds: readonly string[]    // 열려 있는 창. 연 순서
  layerEl: HTMLElement | null   // 창이 그려지는 레이어 요소
  areaSize: Size | null         // 기준 영역의 크기
  gesture: { id: string; type: 'move' | 'resize' } | null
  snapPreview: SnapTarget | null  // 지금 놓으면 적용될 스냅 대상
}

interface WindowLayout {
  windows: Record<string, WindowState>
  order: string[]               // 겹침 순서. 끝이 맨 앞
}

interface WindowState {
  rect: Rect                    // 일반 상태일 때의 자리
  placement: 'normal' | 'minimized' | 'maximized' | { snap: 'left' | 'right' }
  restorePlacement?: 'normal' | 'maximized' | { snap: 'left' | 'right' }
}
```

지켜야 할 규칙은 이렇습니다.

- **`rect` 는 언제나 일반 상태의 자리입니다.** 최대화하거나 스냅해도 바뀌지 않습니다. 실제로 그려지는 자리는 `effectiveRect(창, 영역 크기)` 가 그때그때 계산합니다. 그래서 영역 크기가 바뀌면 최대화·스냅된 창이 저절로 따라가고, "돌아갈 자리"를 따로 저장하지 않습니다.
- **`restorePlacement` 는 최소화된 창에만 있습니다.** 최소화 전의 배치를 기억합니다. 최대화된 창을 최소화했다가 되돌리면 최대화로 돌아옵니다.
- **`windows` 에는 닫힌 창의 자리도 남습니다.** 다시 열면 같은 자리에 나타납니다. `order` 에는 열려 있는 창만 있습니다.
- **상태는 불변으로 갱신합니다.** 한 창을 옮겨도 다른 창의 `WindowState` 객체는 그대로입니다. 구독이 이 성질에 기대고 있습니다.

저장소에는 반응형이 아닌 창별 메타 정보(`minSize`, `maxSize`, `dragInset`, 창 요소, 타이틀바 요소)도 `Map` 으로 들어 있습니다. 제약 계산과 포커스 이동에 씁니다.

## 구독과 렌더

`useManagerState(store, selector)` 는 `useSyncExternalStore` 로 값 하나를 골라 구독합니다. selector 는 원시값이나 저장소가 그대로 들고 있는 참조만 돌려줘야 합니다. 매번 새 객체를 만들어 돌려주면 무한 렌더에 빠집니다.

`Window.Root` 는 다음을 따로따로 구독합니다.

- `layout.windows[id]` (참조)
- `areaSize` (참조)
- `layout.order.indexOf(id)` (숫자)
- `activeId === id` (불리언)
- 이 창의 제스처 종류 (문자열 또는 `null`)
- `layerEl` (참조)

실제 자리는 구독한 값으로 렌더 중에 계산합니다. 창 하나를 끄는 동안 다른 창은 다시 렌더링되지 않습니다. 끌리는 창도 `children` 의 참조가 같아서 내용까지 다시 렌더링하지는 않습니다.

독에 쓰는 `getWindowList()` 는 결과를 `id:배치:활성` 을 이어 붙인 키로 캐시합니다. 창을 옮기는 동안에는 같은 배열을 돌려주고, 배치나 활성 창이 바뀔 때만 새 배열을 만듭니다.

## 기준 영역과 좌표

창이 그려지는 레이어의 상자가 **기준 영역**입니다. 좌표의 원점이고, 이동 제약과 최대화·스냅이 이 상자를 기준으로 계산됩니다.

- `Viewport` 는 `position: fixed` 레이어이고, `Area` 는 부모 안의 `position: absolute` 레이어입니다. 둘은 같은 구현을 쓰고 이 값과 잘라내기만 다릅니다.
- 레이어는 `top`·`right`·`bottom`·`left` 를 0 으로 놓습니다. 사용처가 `style` 로 이 값을 덮어 상자를 줄일 수 있습니다. 독 자리를 비울 때 씁니다.
- `inset` 축약형은 쓰지 않습니다. 사용처가 `bottom` 을 넣었다 빼면 React 가 그 속성만 지워서, 축약형에서 온 0 까지 사라지고 레이어 높이가 무너집니다.
- 영역 크기는 레이어의 `clientWidth`·`clientHeight` 이고 `ResizeObserver` 로 따라갑니다. 크기가 바뀌면 모든 창의 `rect` 에 이동 제약을 다시 적용합니다.
- 포인터 좌표는 `toAreaPoint(clientX, clientY)` 가 레이어의 `getBoundingClientRect()` 를 빼서 영역 좌표로 바꿉니다.
- `Area` 는 `overflow: clip` 으로 영역 밖을 잘라냅니다. `hidden` 이 아닌 이유는, `hidden` 이면 영역 밖에 걸친 창 안의 요소가 포커스를 받을 때 레이어가 스크롤되어 모든 창이 밀리기 때문입니다.

## 레이어 순서

z-index 숫자를 맞추는 대신 **DOM 위치**로 순서를 정합니다.

Base UI 는 앱 루트에 `isolation: isolate` 를 주라고 안내합니다. 그러면 `body` 로 portal 되는 팝업이 앱 내용보다 항상 위에 옵니다. 창 레이어를 그 루트 **안에** 두면 다음 순서가 나옵니다.

| 순서 | 층 | 위치 |
|---|---|---|
| 위 | 다이얼로그, 시트, 팝오버, 메뉴, 툴팁 | `body` 로 portal |
| 중간 | 창 레이어 | 앱 루트 안. 자체 stacking context(`isolation: isolate`) |
| 아래 | 앱 내용 | 앱 루트 안 |

레이어 안에서는 이렇게 합니다.

- 창의 z-index 는 `(order 에서의 위치 + 1) × 2` 입니다. 짝수만 씁니다.
- 스냅 미리보기는 끌고 있는 창 바로 아래의 홀수 자리에 놓입니다.
- **DOM 노드의 순서는 절대 바꾸지 않습니다.** 순서를 바꾸면 창 안의 iframe 이 다시 로드되고 포커스와 스크롤 위치를 잃습니다.

창은 React 의 `createPortal` 로 레이어에 넣습니다. Base UI 의 portal 을 쓰지 않는 이유가 있습니다. Base UI 팝업은 가장 가까운 부모 Base UI portal 안에 렌더됩니다. 창이 Base UI portal 이면 창에서 연 팝업이 창 레이어 안에 갇혀 창 순서에 얽히고, `Area` 에서는 잘립니다.

앱 내용에 z-index 를 쓰는 요소가 있으면 루트 안에서 레이어에 값 하나가 필요합니다(데모는 10). 이 값은 팝업과 경쟁하지 않습니다.

### portal 과 이벤트

React 이벤트는 DOM 이 아니라 React 트리를 따라 올라갑니다. 창에서 연 팝업은 DOM 에서는 `body` 에 있지만 React 트리에서는 창의 자손입니다. 이 성질이 두 군데에 영향을 줍니다.

- **활성화에는 도움이 됩니다.** 창에서 연 메뉴를 눌러도 그 창이 활성화됩니다.
- **제스처에는 방해가 됩니다.** 타이틀바 버튼에서 연 메뉴 항목을 누르면 타이틀바의 `onPointerDown` 까지 올라옵니다. 그래서 제스처 시작과 더블클릭은 `currentTarget.contains(target)` 으로 DOM 포함 관계를 따로 확인합니다.

## 창의 등록과 해제

`Window.Root` 는 열릴 때 `register`, 닫히거나 사라질 때 `unregister` 를 부릅니다.

- **`register`**: 저장된 자리가 있으면 그대로 쓰고, `order` 에 이미 있으면 순서도 유지합니다. 새로 열리는 창은 맨 앞에 오고 활성 창이 됩니다. 자리가 없으면 `defaultRect` 를 쓰고, 위치가 빠져 있으면 48px 에서 시작해 28px 씩 계단식으로 놓습니다.
- **`unregister`**: 실제 제거를 마이크로태스크 하나만큼 늦춥니다. React StrictMode 는 개발 중에 mount → unmount → mount 를 연달아 실행하는데, 그 사이에 다시 `register` 되면 제거를 취소합니다. 이렇게 하지 않으면 복원한 겹침 순서가 mount 할 때마다 뒤섞입니다.
- 창이 그려지려면 네 가지가 모두 있어야 합니다: `open`, 저장소의 창 상태, 레이어 요소, `order` 안의 자리. 레이어가 창보다 늦게 mount 되어도, 레이어 요소가 저장소에 들어오는 순간 창이 다시 렌더링됩니다.

## 활성 창

- 창 요소의 `onPointerDownCapture` 와 `onFocusCapture` 가 `activate(id)` 를 부릅니다. 맨 앞으로 가져오고 활성 창으로 만듭니다.
- 레이어는 `document` 에 `pointerdown` 버블 리스너를 답니다. 어느 창에서도 처리하지 않은 누름이면 활성 창을 풉니다. 겹침 순서는 그대로 둡니다.
- "창에서 처리했다"는 표시는 `WeakMap<Event, Set<관리자>>` 에 **관리자별로** 기록합니다. 한 관리자의 창을 누르면 다른 관리자에게는 바깥 누름이 됩니다. 영역이 여럿일 때 활성 창이 영역별로 독립인 이유입니다.
- 이 순서가 성립하는 것은 React 가 루트 컨테이너에서 이벤트를 받기 때문입니다. 루트 컨테이너는 `document` 보다 아래에 있어서, React 핸들러가 `document` 의 버블 리스너보다 먼저 실행됩니다.

포커스는 세 군데에서 옮깁니다.

- 활성 창이 닫히면 그다음 앞에 있는 보이는 창이 활성 창이 됩니다. 포커스가 `body` 로 떨어졌으면 그 창으로 옮깁니다.
- 최소화할 때도 같습니다. 최소화된 창은 후보에서 뺍니다.
- 최소화에서 되돌린 창이 활성 창이면 포커스를 옮깁니다. 숨겨진 요소에는 `focus()` 가 먹지 않으므로, 다시 보이게 된 커밋 뒤의 layout effect 에서 합니다.

## 이동 제약

제약은 `moveConstraint` 로 고릅니다. 관리자를 만들 때 정해지고 도중에 바꿀 수 없습니다.

### `reachable` (기본)

창이 영역 밖으로 나갈 수 있지만, 타이틀바의 **잡을 수 있는 부분**이 영역 안에 남습니다. "일부가 보인다"가 아니라 "다시 끌어올 수 있다"가 기준입니다.

```
잡을 수 있는 폭 = 창 폭 − dragInset.left − dragInset.right
남길 폭        = min(minVisibleWidth, 잡을 수 있는 폭)

x 의 범위: [남길 폭 + dragInset.right − 창 폭,  영역 폭 − 남길 폭 − dragInset.left]
y 의 범위: [0,  영역 높이 − 타이틀바 높이]
```

- 위쪽으로는 타이틀바가 영역을 넘지 않습니다.
- `minVisibleWidth` 의 기본값은 64 입니다.
- 타이틀바 높이는 타이틀바 요소의 `offsetHeight` 를 잽니다. 아직 못 쟀으면 32 를 씁니다.
- `dragInset` 은 타이틀바 양 끝에서 버튼이 차지하는 폭입니다. 버튼은 잡을 수 없으므로 남길 폭으로 치지 않습니다. 지금은 사용처가 숫자로 넣습니다.

### `contain`

창 전체가 영역 안에 머뭅니다. 창이 영역보다 크면 왼쪽 위에 맞추고 크기는 바꾸지 않습니다. 넘치는 부분은 `Area` 에서 잘립니다.

## 리사이즈

`resizeRect(시작 rect, 잡은 변, 이동량, 옵션)` 가 새 rect 를 구합니다.

- **시작 시점의 rect 를 기준으로 계산합니다.** 이동할 때마다 직전 값에 더해 가지 않으므로 오차가 쌓이지 않습니다.
- **잡지 않은 쪽 변은 움직이지 않습니다.** 왼쪽·위쪽 변을 잡으면 원점이 함께 움직입니다.
- **최소 크기에 닿으면 잡은 변이 멈춥니다.** 창이 밀리지 않습니다.
- `reachable` 에서는 리사이즈 중에도 타이틀바가 닿는 위치에 남도록 변의 범위를 제한합니다. 위쪽 변은 영역 위로 넘어가지 않습니다.
- `contain` 에서는 네 변이 영역을 넘지 않습니다. 최소 크기가 남은 공간보다 크면 최소 크기를 따릅니다.

손잡이는 8개(네 변과 네 모서리)이고 보이지 않는 `div` 입니다. 굵기는 `--window-resize-handle-size`(기본 8px)이고 창 테두리에 반쯤 걸쳐 놓입니다. 모서리는 굵기의 2배 크기입니다. 테두리 밖으로 나가 있으므로 창 요소에 `overflow: hidden` 을 주면 손잡이 절반이 잘립니다.

## 배치

| 배치 | 실제 자리 | 비고 |
|---|---|---|
| `normal` | `rect` | |
| `maximized` | 영역 전체 | 리사이즈 손잡이가 숨겨집니다 |
| `{ snap: 'left' }` | 영역의 왼쪽 절반 | 폭이 홀수면 오른쪽이 1px 넓습니다 |
| `{ snap: 'right' }` | 영역의 오른쪽 절반 | |
| `minimized` | 숨김 | 내용은 마운트된 채 남습니다 |

- **최소화**: 창 요소에 인라인 `display: none` 을 줍니다. `hidden` 속성은 사용처의 `display: flex` 같은 지정에 지기 때문입니다. 최소화된 창을 다시 여는 곳은 사용처가 `useWindowList()` 로 만듭니다.
- **끌어서 풀기**: 최대화·스냅된 창의 타이틀바를 끌면 일반 크기로 풀립니다. `detachRect` 가 포인터가 타이틀바에서 차지하던 가로 비율을 유지하되, 버튼 영역 위에 놓이지 않게 합니다. 이동량은 처음 누른 지점부터 재므로 첫 이동이 멀리 튀어도 타이틀바가 포인터를 따라옵니다.
- **리사이즈**: 스냅된 창을 리사이즈하면 그 자리에서 일반 상태가 됩니다. 최대화된 창은 리사이즈하지 않습니다.
- **`maxSize`**: 최대화와 스냅은 `maxSize` 를 무시합니다.

## 끌어서 스냅

`snap` 옵션을 켰을 때만 동작합니다.

- **판정은 포인터 위치로 합니다.** 창의 변이 아닙니다. 포인터가 가장자리에서 `threshold`(기본 8px) 안에 들어오면 대상이 됩니다. 왼쪽·오른쪽은 절반, 위쪽은 최대화이고 모서리에서는 좌우가 우선합니다.
- **가장자리 바깥의 좌표도 띠 안으로 칩니다.** 포인터가 영역을 벗어나도 대상이 유지됩니다. 뷰포트의 가장자리는 화면 끝처럼 포인터를 물리적으로 멈춰 주지 않기 때문에 필요합니다.
- **한번 잡힌 대상은 더 넓은 띠를 벗어날 때까지 유지합니다.** 가장자리에서 `threshold + release`(기본 8 + 24 = 32px) 밖으로 나가야 풀립니다. 사용자는 미리보기가 뜨는 순간 멈추므로 포인터가 경계 바로 위에 있는데, 버튼을 놓으며 손이 몇 px 흔들리면 대상이 풀려 버리는 것을 막습니다.
- **놓을 때만 적용합니다.** 끄는 동안에는 `snapPreview` 만 바뀝니다. 브라우저가 포인터를 취소하면 미리보기만 지웁니다.
- **돌아갈 자리는 끌기 전의 자리입니다.** 제스처를 시작할 때의 `rect` 를 기억해 두었다가, 스냅을 적용할 때 그 값을 `rect` 로 남깁니다. 그러지 않으면 스냅을 풀었을 때 창이 끌려온 가장자리에 놓입니다.

지키는 불변식은 하나입니다. **미리보기가 보이면 놓았을 때 반드시 적용됩니다.**

## 제스처의 수명

이동과 리사이즈는 같은 구조를 씁니다.

1. 손잡이(타이틀바 또는 리사이즈 손잡이)의 `onPointerDown` 에서 가드를 통과하면 세션을 만듭니다.
2. `window` 에 캡처 단계 리스너(`pointermove`, `pointerup`, `pointercancel`)를 붙입니다.
3. 세션이 끝나면 리스너를 뗍니다.

시작 가드는 넷입니다.

- 주 버튼(왼쪽 버튼)일 것
- 진행 중인 세션이 없을 것
- 누른 대상이 손잡이의 DOM 안에 있을 것 (portal 을 타고 온 이벤트를 거릅니다)
- 타이틀바라면 인터랙티브 요소가 아닐 것 (버튼, 링크, 입력 요소, `[role="button"]`, `[role="menuitem"]`, `contenteditable`, `data-window-no-drag`)

세션이 끝나는 조건은 셋뿐입니다.

| 조건 | 결과 |
|---|---|
| `pointerup` | 스냅을 적용하며 끝 |
| `pointercancel` | 적용하지 않고 끝 |
| 버튼이 떼어진 채로 온 `pointermove` (`buttons === 0`) | 놓은 것으로 보고 적용하며 끝 |

**pointer capture 를 잃는 것은 끝나는 조건이 아닙니다.** 손잡이에 capture 를 걸긴 하지만 보조일 뿐입니다. capture 는 버튼을 놓기 전에도 풀릴 수 있고, 실제 마우스로 가장자리에 놓았을 때 `lostpointercapture` 가 `pointerup` 보다 먼저 오는 것이 관측됐습니다. 그것을 끝으로 삼으면 미리보기가 떠 있던 스냅이 버려집니다. 자세한 경위는 [스냅 드롭 문제 조사](./investigations/snap-drop.md)에 있습니다.

창이 포커스를 잃어도(`blur`) 제스처를 끝내지 않습니다. capture 를 잃는 원인이 포커스일 가능성을 배제하지 못했기 때문입니다. `pointerup` 을 못 받은 채 끝난 제스처는 다음 이동에서 `buttons === 0` 으로 정리됩니다.

그 밖의 세부는 이렇습니다.

- **이동 임계값**: 타이틀바는 3px 움직인 뒤에야 이동을 시작합니다. 눌렀다 떼는 것만으로 창이 밀리지 않게 합니다. 리사이즈는 첫 이동에서 시작합니다.
- **끌기 뒤의 더블클릭**: 끌다가 놓아도 `click` 이 타이틀바에 발생합니다. 타이틀바를 한 번 누른 직후 다시 눌러 끌면 그 `click` 이 두 번째 클릭으로 집계되어 `dblclick` 이 따라올 수 있습니다. 가장 최근의 누름이 끌기로 이어졌으면 더블클릭 최대화를 무시합니다.
- **사용처의 핸들러**: 라이브러리는 손잡이의 `onPointerDown` 만 감쌉니다. 사용처의 핸들러가 먼저 실행되고, `preventDefault()` 하면 제스처를 시작하지 않습니다.

## 배치 변경 알림

`onLayoutChange` 는 `layout` 이 바뀔 때 마이크로태스크로 한 번 모아서 부릅니다.

- **제스처 도중에는 알리지 않습니다.** 이동·리사이즈가 끝났을 때 한 번 알립니다.
- **리스너가 붙기 전의 변화는 알리지 않습니다.** 처음 mount 될 때의 창 등록이 여기에 해당합니다. 리스너가 붙는 시점의 배치를 기준으로 삼기 때문에, effect 와 마이크로태스크의 실행 순서에 결과가 좌우되지 않습니다.
- **활성 창만 바뀌면 알리지 않습니다.** `activeId` 는 `layout` 밖에 있습니다. 다만 창을 눌러 맨 앞으로 오면 `order` 가 바뀌므로 알립니다.

## 접근성 현황

- 창 요소는 `role="dialog"` 이고 `aria-labelledby` 로 `Window.Title` 을 가리킵니다. `aria-modal` 은 없습니다(비모달).
- 창 요소는 `tabIndex={-1}` 이라 프로그램으로 포커스를 받을 수 있습니다.
- 바깥을 누르거나 Escape 를 눌러도 닫히지 않습니다.
- 리사이즈 손잡이와 스냅 미리보기는 `aria-hidden` 입니다.
- 키보드로 창을 옮기거나 크기를 바꾸는 기능은 없습니다. 창을 열어도 포커스가 창으로 가지 않습니다. [로드맵](./roadmap.md)에 있습니다.
