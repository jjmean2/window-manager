# 로드맵

구현한 것, 남은 것, 알려진 한계입니다. 일정은 정해져 있지 않습니다.

이 프로토타입의 목적은 Base UI 와 shadcn 을 바탕으로 한 디자인 시스템에 넣을 창 관리자 컴포넌트를 미리 만들어 보는 것입니다. 남은 일은 "그 디자인 시스템으로 옮기는 데 무엇이 필요한가"를 기준으로 정리했습니다.

## 구현한 것

처음 주어진 요구는 모두 들어가 있습니다.

| 단계 | 내용 |
|---|---|
| 1 | 관리자, 뷰포트 영역, 타이틀바 이동, 8방향 리사이즈, 겹침 순서, 활성 창, 이동 제약, 배치 저장과 복원 |
| 2 | 최소화, 최대화, 좌우 절반 스냅, 끌어서 스냅과 미리보기, 타이틀바 더블클릭, 끌어서 풀기, 독을 위한 창 목록 |
| 3 | 영역 한정(`Area`), 영역별 활성 창, 창 전체를 영역 안에 두는 이동 제약 |

### 확인 수준

브라우저 확인은 대부분 자동화 도구가 보낸 입력으로 했습니다. 자동화 도구의 드래그는 누름, 한 번의 이동, 놓기로 끝나서 손으로 끌 때와 다릅니다. 이 차이 때문에 놓친 문제가 있었고, 경위는 [조사 기록](./investigations/snap-drop.md)에 있습니다.

| 수준 | 대상 |
|---|---|
| 사람이 실제 마우스로 확인 | 가장자리에 끌어 놓았을 때 스냅이 적용되는 것 (수정 뒤의 진단 줄 1건) |
| 브라우저에서 자동화 도구의 입력으로 확인 | 이동, 8방향 리사이즈, 앞으로 가져오기, 화면 밖 제약, 최소화·최대화·스냅, 영역 한정에서의 잘림과 영역별 활성 창, 메뉴·팝오버·모달의 레이어 순서, 새로고침 후 복원 |
| 브라우저에서 합성 이벤트로 확인 | 놓기 직전의 포인터 흔들림, pointer capture 를 잃은 뒤의 놓기, 브라우저의 포인터 취소 |
| 단위 테스트로만 확인 | 스냅 미리보기가 끄는 도중 사라지는 경우, `contain` 에서의 리사이즈, 제스처 도중 창이 닫히는 경우 |
| 확인하지 못함 | 터치·펜 입력, 창에서 연 팝업 안을 눌렀을 때의 창 활성화, 툴팁·시트와의 레이어 순서, 모달이 열린 동안 키보드로 창에 닿을 수 있는지, 실제 `PanelLayout` 과의 조합 |

단위 테스트는 112개이고, 모두 React 와 무관한 모듈을 다룹니다. 브라우저 확인은 한 번씩 한 것이고 반복해서 실행되는 테스트가 아닙니다.

## 남은 일

### 지금 코드만으로 할 수 있는 것

권장 순서대로 적었습니다.

1. **키보드 지원.** 키보드로 창을 옮기거나 크기를 바꿀 수 없고, 창을 열어도 포커스가 창으로 가지 않습니다. 접근성 요건이라 가장 먼저 필요합니다. 창 사이를 키보드로 오가는 방법도 정해야 합니다.
2. **React 파트의 자동 테스트.** 파트 조합, 포커스 이동, portal 을 통한 이벤트 가드는 브라우저에서 자동화 도구로 한 번씩만 확인했습니다. 합성 `PointerEvent` 로 제스처 순서를 재현하는 방법은 [조사 기록](./investigations/snap-drop.md)에 있습니다.
3. **이름.** `Window` 는 import 한 모듈에서 전역 `Window` 를 가립니다.
4. **`dragInset` 자동 측정.** 타이틀바의 버튼 폭을 지금은 사용처가 숫자로 넣습니다. 빠뜨리면 버튼만 보이고 잡을 곳이 없는 위치까지 창이 나갈 수 있습니다.
5. **터치·펜 입력 확인.** 코드는 포인터 이벤트 기반이고 손잡이에 `touch-action: none` 을 주지만, 실제 기기에서 확인한 적이 없습니다.
6. **패키지 빌드.** 지금은 소스를 그대로 export 합니다. 배포하려면 빌드와 타입 선언 출력이 필요합니다.
7. **기본 스타일 래퍼.** headless 프리미티브 위에 디자인 시스템의 모양을 입힌 기본 창이 없습니다. 데모의 `AppWindow` 가 출발점입니다.

### 대상 디자인 시스템의 코드가 있어야 하는 것

실제 `PanelLayout`·`SplitLayout` 의 API 와 구현을 봐야 정할 수 있습니다.

- **제어형 `layout` prop.** 지금은 비제어형만 됩니다. 기존 레이아웃 컴포넌트의 상태 관례에 맞춰야 합니다. 제스처가 끝날 때만 알리는 방식과 제어형이 어떻게 맞물릴지도 정해야 합니다.
- **`render` prop 관례.** Base UI 처럼 요소를 바꿔 끼우는 방식을 지원하지 않습니다.
- **hover 로 뜨는 SidePanel overlay 를 창 위에 두기.** 그렇게 하기로 정했지만 만들지도 확인하지도 못했습니다. overlay 가 어디에 그려지는지에 따라 방법이 달라집니다([결정 기록 D7](./decisions.md)).
- **앱 루트가 `isolation: isolate` 인지 확인.** 아니라면 레이어 순서를 z-index 토큰으로 잡아야 합니다([결정 기록 D6](./decisions.md)).

### 범위에서 뺀 것

- **레이아웃 패널로의 편입.** 창을 `PanelLayout`·`SplitLayout` 의 패널로 옮겨 넣는 도킹은 하지 않기로 했습니다. 한다면 창의 내용이 두 레이아웃 트리 사이를 옮겨 다녀야 합니다.
- **모서리 스냅(1/4).** 좌우 절반과 최대화만 있습니다.

## 정해지지 않은 것

- **위쪽 스냅의 판정 방식.** 포인터 위치 기준을 유지하는 것을 권하지만 확답을 받지 못했습니다. 타이틀바 아래쪽을 잡으면 창이 멈춘 뒤에도 더 밀어 올려야 스냅됩니다. 까다로우면 `threshold` 를 키웁니다([결정 기록 D13](./decisions.md)).
- **끌어서 스냅의 기본값.** 지금은 꺼져 있습니다.

## 알려진 한계

- **iframe 위에서의 이동.** pointer capture 가 풀린 상태에서는 포인터가 창 안의 iframe 위를 지날 때 이동이 끊길 수 있습니다.
- **영역이 여럿일 때의 활성 창.** 활성 창 해제는 포인터 누름에만 걸려 있습니다. 키보드로 포커스만 옮기면 두 영역의 창이 동시에 활성일 수 있습니다.
- **모달 안의 창.** 모달 안에서 연 창은 그 모달이 닫힐 때까지 쓸 수 없습니다.
- **영역이 잠깐 줄어드는 경우.** 영역이 줄면 밖에 놓인 창이 안으로 당겨지고, 영역이 다시 늘어나도 돌아가지 않습니다. 스크롤바가 잠깐 나타나는 경우에도 생깁니다.
- **버튼을 놓기 전에 capture 가 먼저 풀리는 원인.** 확인하지 못했습니다. 동작은 정상입니다([조사 기록](./investigations/snap-drop.md)).
- **`Area` 에서의 스냅.** 포인터가 영역 밖으로 나가기만 해도 스냅 대상이 됩니다.

## 정리할 것

- **데모의 "마지막 드롭" 진단 줄.** 스냅 문제를 조사하려고 넣었습니다. 용도가 끝났으니 지울 수 있습니다.
