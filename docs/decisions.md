# 결정 기록

무엇을 정했고 왜 그렇게 정했는지 적습니다. 각 항목에 누가 정했는지를 표시했습니다.

- **요구**: 처음부터 주어진 요구 사항입니다.
- **결정**: 선택지를 두고 프로젝트 소유자가 고른 것입니다.
- **구현 중 판단**: 구현하면서 정한 것입니다. 소유자가 따로 확인하지 않았습니다.
- **미확정**: 권장안은 있지만 확답을 받지 못했습니다.

## 출발점

대상은 Base UI 와 shadcn 을 바탕으로 한 디자인 시스템입니다. 거기에는 영역을 headless 로 관리하는 레이아웃 컴포넌트가 이미 있습니다.

- `PanelLayout`: 좌우 SidePanel 과 중앙 Main 을 두고, SidePanel 을 리사이즈하거나 접습니다. 접힌 SidePanel 은 Main 위에 overlay 로 나타날 수 있습니다.
- `SplitLayout`: 영역을 분할하고 리사이즈하거나 접습니다.

같은 수준에서 "데스크톱처럼 자유롭게 옮기고 크기를 바꾸는 창"을 제공하는 컴포넌트가 목표였습니다. 이 저장소는 그 프로토타입입니다.

처음 주어진 요구는 이렇습니다.

| 요구 | 반영 |
|---|---|
| 특정 영역 안에서만 움직이는 것도 지원하되, 우선은 뷰포트 전체 | `Viewport` 가 기본, `Area` 로 영역 한정 |
| 네 모서리와 네 변으로 크기 변경 | 손잡이 8개 |
| 타이틀바의 버튼이 아닌 부분을 잡고 이동 | 인터랙티브 요소 제외 가드 |
| 영역 밖으로 나갈 수 있지만 다시 끌어올 수 있게 일부는 남김 | `moveConstraint: 'reachable'` |
| 영역 밖으로 나간 부분을 자를지는 미정 | D5 |
| 다이얼로그·툴팁과의 레이어 관계는 미정 | D6 |
| 최소화, 최대화, 특정 위치에 도킹 | D9, D10 |

## D1. 가져다 쓰지 않고 관리 층을 직접 만든다 (결정)

조사에서 가장 근접한 것은 Ark UI 의 `FloatingPanel` 이었습니다. 그러나 레이아웃 수준의 컴포넌트가 아니라 "열었다 닫는 창 하나"짜리 오버레이였습니다.

- 창의 집합을 가진 부모가 없습니다. `Root` 하나가 상태 머신 하나입니다.
- 겹침 순서 스택이 모듈 전역입니다. 영역이 둘이면 순서와 "맨 위" 판정이 섞입니다.
- 좌표가 뷰포트 기준입니다. 저장한 위치가 영역 기준이 아닙니다.
- `role="dialog"` 이고 Trigger 로 열고 닫으며 Escape 로 닫힙니다.

그래서 창 목록·영역별 순서·영역 기준 좌표·배치 상태를 가진 관리 층을 직접 만들고, 드래그·리사이즈 같은 창 하나의 동작은 Zag.js 의 `floating-panel` 을 참고 구현으로 삼았습니다. 의존성으로 넣지는 않았습니다.

근거가 된 조사는 [사전 조사](./research.md)에 있습니다.

## D2. 레이아웃 컴포넌트와 같은 계층의 headless 프리미티브로 만든다 (요구)

`PanelLayout`·`SplitLayout` 과 같은 계층이지만 성격이 다릅니다. 그쪽은 공간을 **나누고**, 창 관리자는 영역 위에 **덧씌웁니다**. 공간을 차지하지 않고, 겹침 순서라는 상태가 추가됩니다.

동작은 headless 로 제공하고 모양은 사용처가 정합니다.

- **프리미티브가 맡는 것**: 창 목록·순서·활성 상태, 좌표와 이동 제약, 제스처, 배치 전환, ARIA 속성. 상태는 data 속성으로 내보냅니다.
- **사용처가 정하는 것**: 타이틀바 생김새, 버튼 종류와 배치, 테두리와 그림자, 리사이즈 손잡이의 굵기, 최소화된 창을 보여 줄 독.

디자인 시스템에서는 shadcn 이 Base UI 를 감싸는 것처럼 두 겹을 권합니다. headless 프리미티브 위에 기본 스타일을 입힌 래퍼를 두는 구조입니다. **래퍼는 아직 없습니다.** 데모의 `AppWindow` 가 그 자리에 해당합니다.

## D3. 기준 영역과 이동 제약을 분리한다 (구현 중 판단)

"창이 어디에 사는가"와 "얼마나 벗어날 수 있는가"는 별개입니다.

- **기준 영역**: 좌표 원점, 렌더 위치, 잘림을 정합니다. 관리자는 항상 기준 영역 하나를 갖고, 뷰포트는 그 기본값입니다.
- **이동 제약**: 창이 영역을 얼마나 벗어날 수 있는지를 정합니다.

대상 앱은 "기준 영역 = 뷰포트, 이동 제약 = 일부는 남김"입니다.

## D4. 이동 제한은 "타이틀바를 다시 잡을 수 있는가"로 정한다 (구현 중 판단)

요구는 "화면 안에 일부는 남도록"이었습니다. "몇 px 이 보인다"로 구현하면 버튼만 보이고 잡을 곳이 없는 상태가 생깁니다. 그래서 타이틀바에서 버튼이 아닌 부분이 일정 폭(기본 64px) 남는 것을 기준으로 삼았습니다. 위쪽으로는 타이틀바가 영역을 넘지 않습니다.

## D5. 오버플로우: 뷰포트는 그대로, 영역 한정은 잘라낸다 (구현 중 판단)

- 뷰포트 영역에서는 정할 것이 없습니다. 브라우저가 자르고, `fixed` 요소는 스크롤바를 만들지 않습니다.
- 영역 한정에서는 잘라냅니다. 자르지 않으면 창이 옆 SidePanel 위로 그려지는데, 그 영역과는 겹침 순서가 정의돼 있지 않습니다.

## D6. 레이어 순서는 DOM 위치로 정한다 (구현 중 판단)

창 레이어를 `isolation: isolate` 인 앱 루트 안에 둡니다. `body` 로 portal 되는 다이얼로그·시트·팝오버·툴팁이 숫자 계산 없이 모든 창 위에 옵니다.

따라오는 결과가 있습니다.

- 창 안에서 연 팝오버는 모든 창 위에 뜹니다. 다른 창을 누르면 바깥 누름으로 닫힙니다.
- 모달은 창을 덮고 바깥 조작을 막습니다. **모달 안에서 연 창은 그 모달이 닫힐 때까지 쓸 수 없습니다.**
- 앱 내용에 z-index 를 쓰는 요소가 있으면 루트 안에서 레이어에 값 하나가 필요합니다. "z-index 없이"라고 처음에 설명한 것은 정확하지 않았습니다.

전제가 하나 있습니다. **대상 앱의 루트가 `isolation: isolate` 라는 것은 확인된 사실이 아니라 소유자의 기억입니다.** 아니라면 레이어에 shadcn 의 `z-50` 보다 낮은 토큰을 주는 방식으로 바꿉니다.

## D7. hover 로 뜨는 SidePanel overlay 는 창 위에 둔다 (결정, 미구현)

접힌 SidePanel 은 마우스를 올린 동안 잠시 떠서 Main 을 덮습니다. 이것은 창 위에 두기로 했습니다.

- 잠깐 뜨는 것이 계속 떠 있는 것보다 위라는 것은 팝오버·툴팁과 같은 원칙입니다.
- 반대로 두면 창이 화면 가장자리에 걸쳐 있을 때 패널이 창 밑에서 열려 가려집니다.

처음에는 "창이 위"를 권했다가 소유자의 지적으로 뒤집었습니다.

**이 저장소에는 `PanelLayout` 이 없어 만들지도 확인하지도 못했습니다.** 실제 구현에서는 overlay 가 어디에 그려지는지에 달려 있습니다. 레이아웃 안에 그려진다면 `body` 로 portal 하는 쪽을 권합니다. 루트 안에서 z-index 로 올리는 방법은 조상 중에 stacking context 를 만드는 요소가 있으면 통하지 않습니다.

## D8. 창을 Dialog 위에 만들지 않는다 (구현 중 판단)

Base UI 의 `Dialog` 는 `modal={false}` 여도 바깥 누름과 포커스 이탈로 닫히는 것이 기본입니다. 창은 다른 곳을 눌러도 남아 있어야 하고 Escape 로 닫히지도 않습니다. 그래서 별도 프리미티브로 만들고 비모달 `role="dialog"` 와 `aria-labelledby` 만 붙였습니다.

## D9. 최대화는 기준 영역을 채운다 (결정)

뷰포트 영역이면 뷰포트 전체, 영역 한정이면 그 영역입니다. "뷰포트 전체인가 Main 인가"를 두고 기준 영역과 일치시키는 쪽으로 정했습니다.

독이나 상단 바가 있으면 최대화된 창이 그것을 덮습니다. 이를 피하려고 `Viewport` 의 `style` 로 기준 영역을 줄일 수 있게 했습니다(D17).

## D10. 도킹은 가장자리 스냅으로 한정한다 (결정)

"도킹"에는 두 뜻이 있었습니다.

- 가장자리 스냅: 창이 창 레이어 안에 남고 자리만 정해집니다.
- 레이아웃 패널로 편입: 창의 내용이 `PanelLayout`·`SplitLayout` 의 패널로 옮겨 갑니다.

가장자리 스냅만 하기로 했습니다. 편입은 내용이 두 레이아웃 트리 사이를 옮겨 다녀야 해서 규모가 다릅니다. 범위에서 뺐습니다.

## D11. `rect` 는 일반 상태의 자리이고, 최대화·스냅 자리는 계산한다 (구현 중 판단)

처음 설계에는 "돌아갈 자리"를 저장하는 `restoreRect` 가 있었습니다. 구현하면서 없앴습니다.

- `rect` 를 항상 일반 상태의 자리로 두면 돌아갈 자리를 따로 저장할 필요가 없습니다.
- 최대화·스냅 자리를 영역에서 계산하면 영역 크기가 바뀔 때 저절로 따라갑니다.

대신 최소화된 창이 돌아갈 **배치**를 기억하는 `restorePlacement` 가 생겼습니다.

## D12. 끌어서 스냅은 옵션이고 기본은 꺼 둔다 (구현 중 판단)

스냅은 "창을 화면 밖에 걸쳐 둘 수 있다"는 요구와 부딪힙니다. 포인터가 좌우 가장자리에 닿으면 스냅이 걸리므로, 그쪽으로 창을 걸치려면 타이틀바의 반대쪽 끝을 잡아야 합니다. 그래서 `snap` 옵션으로 두고 기본은 껐습니다.

위쪽 가장자리를 최대화로 쓰는 것은 "가장자리 스냅"에 덧붙인 것입니다. `snap={{ top: false }}` 로 끕니다.

## D13. 스냅 판정은 포인터 위치로 한다 (미확정)

스냅은 창의 변이 아니라 포인터가 가장자리 띠 안에 있는가로 판정합니다. Windows, macOS, KDE 의 창 관리자가 모두 이 방식입니다.

이 방식에는 알려진 성질이 있습니다. 위쪽에서는 창이 영역 위에서 멈추지만 포인터는 타이틀바 안에서 잡은 높이에 있습니다. 타이틀바 아래쪽을 잡았으면 창이 멈춘 뒤에도 더 밀어 올려야 합니다.

이를 "창이 멈춘 뒤 더 밀어 올린 거리"로 판정하자는 대안을 한때 권했다가, 관례가 아니어서 **철회했습니다**. 현재 권장은 그대로 두는 것이고, 까다로우면 `threshold` 를 키우는 것입니다. 소유자는 관례를 물은 뒤 확답하지 않았습니다.

## D14. 제스처의 수명을 pointer capture 에 묶지 않는다 (구현 중 판단)

처음에는 손잡이에 capture 를 걸고 `lostpointercapture` 를 "취소"로 처리했습니다. 실제 마우스로 가장자리에 놓을 때 `lostpointercapture` 가 `pointerup` 보다 먼저 와서, 미리보기가 떠 있던 스냅이 버려졌습니다.

지금은 `window` 에서 이동·놓기·취소를 듣고, capture 는 보조로만 겁니다. 경위는 [스냅 드롭 문제 조사](./investigations/snap-drop.md)에 있습니다.

## D15. 배치는 비제어형으로만 제공한다 (구현 중 판단)

`defaultLayout`, `onLayoutChange`, `useWindowManager().setLayout()` 으로 저장하고 복원합니다. 제어형 `layout` prop 은 없습니다.

설계 단계에서는 제어형도 제공한다고 했습니다. 제스처가 끝날 때만 알리는 방식과 제어형이 맞물리는 지점(끄는 동안 내부 상태가 prop 과 어긋남)을 풀지 않았고, 대상 디자인 시스템의 상태 관례를 보고 맞추는 편이 낫다고 판단해 미뤘습니다.

## D16. 영역마다 관리자를 따로 둔다 (구현 중 판단)

관리자 하나는 기준 영역 하나를 갖습니다. 영역이 여럿이면 `WindowManager.Root` 를 여러 개 둡니다. 겹침 순서, 활성 창, 저장되는 배치가 영역별로 독립입니다.

## D17. 요구에 없던 추가 (구현 중 판단)

- **`moveConstraint="contain"`**: 창 전체가 영역 안에 머뭅니다. "영역 안에서만 움직이게"라는 요구를 문자 그대로 만족시키려고 넣었습니다.
- **`Viewport` 의 `style` 로 기준 영역 줄이기**: 독이나 상단 바의 자리를 비우려고 넣었습니다. 없으면 최대화된 창이 독을 덮습니다.

## D18. `.claude/worktrees/` 는 저장소에서 무시한다 (구현 중 판단)

Claude Code 가 작업용으로 만드는 git worktree 입니다. Claude Code 문서의 안내대로 `.gitignore` 에 `.claude/worktrees/` 만 추가했습니다. `.claude/` 의 나머지는 공유하는 파일이라 무시하지 않습니다.
