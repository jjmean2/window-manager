# 조사 기록: 가장자리에 놓았는데 스냅이 안 되는 문제

끌어서 스냅을 켠 상태에서, 창을 가장자리로 끌어 놓았는데 간헐적으로 스냅되지 않는다는 보고가 있었습니다. 원인을 찾는 데 세 번의 시도가 필요했습니다. 앞의 두 번은 실제 결함을 고쳤지만 보고된 증상의 원인은 아니었습니다.

같은 부류의 문제를 다시 만났을 때 참고하도록 경위를 남깁니다.

## 요약

| 순서 | 가설 | 고친 것 | 보고된 증상의 원인이었나 |
|---|---|---|---|
| 1 | 끌기 뒤에 더블클릭이 따라와 스냅을 뒤집는다 | 끌기로 이어진 누름의 더블클릭을 무시 | 아니었음 |
| 2 | 놓는 순간 포인터가 판정 띠를 벗어난다 | 잡힌 대상을 더 넓은 띠에서 유지 | 아니었음 |
| 3 | pointer capture 를 잃은 것을 취소로 처리한다 | 제스처의 수명을 capture 에 묶지 않음 | **맞았음** |

## 왜 자동화로 재현되지 않았나

브라우저 자동화 도구의 드래그는 누름 → 한 번의 이동 → 놓기로 끝납니다. 손으로 끌 때의 성질이 빠져 있습니다.

- 이동이 한 번뿐이라 "놓기 직전의 작은 움직임"이 없습니다.
- 클릭 횟수(`detail`)를 도구가 정합니다. "두 번째 클릭이면서 끌기"를 만들 수 없습니다.
- 이벤트 순서가 항상 `pointerup` → `lostpointercapture` 입니다.

그래서 코드 경로는 **합성 `PointerEvent`** 로 확인했습니다. 타이틀바의 `setPointerCapture`·`hasPointerCapture`·`releasePointerCapture` 를 잠시 no-op 으로 바꾸고, 원하는 순서대로 이벤트를 보내는 방식입니다. 합성 이벤트는 코드 경로만 증명합니다. 실제 하드웨어에서 그 순서가 생기는지는 따로 확인해야 합니다.

## 1. 끌기 뒤의 더블클릭

**가설.** 타이틀바의 더블클릭은 최대화 전환입니다. 끌다가 놓아도 `click` 이 타이틀바에 발생합니다. 타이틀바를 한 번 누른 직후 같은 자리를 다시 눌러 끌면, 놓을 때의 `click` 이 두 번째 클릭으로 집계되어 `dblclick` 이 따라옵니다. 위쪽 스냅(최대화)은 곧바로 일반 상태로 뒤집히고, 좌우 스냅은 최대화로 바뀝니다.

**확인한 것.**

- 브라우저에서 확인: 끌기 뒤에 `click` 이 타이틀바를 대상으로 발생합니다.
- 브라우저에서 확인: 수정 후에는 끌기 직후의 `dblclick` 이 무시되고, 일반 더블클릭은 그대로 동작합니다.
- 추론: "두 번째 클릭으로 집계된다"는 부분은 도구로 만들 수 없어 확인하지 못했습니다.

**수정.** 가장 최근의 누름이 끌기로 이어졌으면 더블클릭 최대화를 무시합니다.

**결과.** 증상이 계속됐습니다. 보고자가 "미리보기는 떴는데 스냅이 안 된다"고 구체화했습니다.

## 2. 놓는 순간 판정 띠를 벗어남

**가설.** 스냅 대상은 포인터가 가장자리 8px 안에 있을 때만 잡히고, 이동할 때마다 같은 8px 로 다시 판정했습니다. 사용자는 미리보기가 뜨는 순간 멈추므로 포인터가 경계 바로 위에 있습니다. 버튼을 놓으며 손이 몇 px 흔들리면 마지막 이동이 띠 밖으로 나가 대상이 풀리고, 곧바로 이어지는 놓기는 스냅 없이 끝납니다.

**확인한 것.**

- 브라우저에서 확인(합성 이벤트): x=6 에서 미리보기가 뜬 뒤 x=9 로 움직이고 놓으면, 그 순간 미리보기는 DOM 에 남아 있는데 결과는 스냅되지 않았습니다.
- 브라우저에서 확인(합성 이벤트): 수정 후 같은 순서에서 스냅이 적용됩니다. 54px 되돌아가면 미리보기가 사라집니다.

**수정.** 한번 잡힌 대상은 가장자리에서 `threshold + release`(기본 32px) 밖으로 나갈 때까지 유지합니다.

**결과.** 증상이 계속됐습니다. 이 시점에 데모에 진단 줄을 넣었습니다.

## 3. pointer capture 상실을 취소로 처리

**진단 줄.** 타이틀바를 끌다 놓을 때마다, 어떤 이벤트가 어떤 순서로 왔고 그때 미리보기가 있었는지를 한 줄로 보여 줍니다. 라이브러리보다 먼저 보도록 `window` 의 캡처 단계에서 듣습니다. 데모의 상태 패널과 콘솔에 나옵니다.

**보고된 줄 (수정 전).**

```
settings: 종료 lostpointercapture → pointerup · 마지막 이동 0,344 · 놓은 곳 1,345 ·
놓을 때 미리보기 left · 결과 normal
```

`lostpointercapture` 가 `pointerup` 보다 먼저 왔습니다. 평소에는 반대 순서입니다. 당시 코드는 `lostpointercapture` 를 "제스처가 취소됐다"로 보고 스냅 없이 끝냈고, 바로 뒤에 온 `pointerup` 은 이미 끝난 제스처라 무시됐습니다.

**확인한 것.**

- 브라우저에서 확인(합성 이벤트): 같은 순서를 만들면 수정 전에는 보고된 것과 같은 줄이 나옵니다.
- 브라우저에서 확인(합성 이벤트): 수정 후 같은 순서에서 스냅이 적용됩니다. 끄는 도중에 capture 를 잃어도 창이 계속 따라오고, 그 뒤 놓으면 스냅됩니다. `pointercancel` 에서는 스냅되지 않습니다.
- 브라우저에서 확인(실제 입력): 이동, 가장자리 스냅, 리사이즈, 더블클릭, 메뉴 항목에서 시작한 끌기가 기존대로 동작합니다.

**수정.** 제스처의 수명을 capture 에 묶지 않습니다. 누른 뒤의 이동·놓기·취소는 `window` 에서 듣고, capture 는 보조로만 겁니다. 끝나는 조건은 `pointerup`, `pointercancel`, 버튼이 떼어진 채로 온 이동 셋뿐입니다. 판정은 React 와 무관한 모듈(`gesture.ts`)로 분리하고 단위 테스트를 붙였습니다.

**보고된 줄 (수정 후).**

```
settings: lostpointercapture@2133,499(미리보기 right) → pointerup@2133,499(미리보기 없음) ·
마지막 이동 2133,499 · capture 상실 시 타이틀바 붙어 있음, 포커스 있음, 그 뒤 이동 1회 ·
창 blur 없음 · 결과 snap-right
```

스냅이 적용됐습니다. 실제 마우스에서 수정이 동작하는 것이 확인됐습니다.

## 원인에 대해 아는 것과 모르는 것

**로그에서 확정된 것.**

- 놓는 순간에 일어납니다. 세 이벤트가 같은 좌표에서 왔습니다.
- 앱 안의 문제가 아닙니다. capture 를 잃을 때 타이틀바는 문서에 붙어 있었고, 포커스가 있었고, 창 `blur` 도 없었습니다.
- 두 번 모두 화면 끝이었습니다(x=0, x=2133).

**로그와 코드에서 추론한 것.**

- `pointerup` 보다 먼저 "버튼이 떼어진 이동"이 도착합니다. 수정 후 줄에서 `pointerup` 시점에 미리보기가 이미 없는데 결과는 스냅입니다. 제스처가 그 앞의 이동 1회에서 끝났다는 뜻이고, 라이브러리가 이동에서 끝내는 경우는 버튼이 떼어진 이동뿐입니다.
- 브라우저가 그 이동을 보내기 전에 capture 를 푸는 것으로 보입니다.

**모르는 것.**

- 이 순서가 왜 화면 끝에서만 생기는지. 운영체제 쪽인지 브라우저 쪽인지 확인하지 못했습니다.
- 다른 운영체제와 브라우저에서도 같은지.

수정은 원인과 무관하게 동작합니다. 같은 순서로 오는 한 스냅은 빠지지 않습니다.

## 얻은 것

- **"미리보기가 보이면 놓았을 때 반드시 적용된다"** 를 불변식으로 삼고 테스트로 묶었습니다.
- **pointer capture 는 이벤트를 모아 주는 편의일 뿐, 제스처가 살아 있다는 보증이 아닙니다.** 제스처를 끝내는 신호로 쓰면 안 됩니다.
- **간헐적인 입력 문제는 추측보다 로그가 빠릅니다.** 가설 두 개를 세워 고치는 동안 왕복이 두 번 더 났고, 진단 줄 하나로 경로가 확정됐습니다.
- 진단 줄은 데모(`apps/playground/src/App.tsx` 의 `LastDrop`)에 남아 있습니다. 동작에는 영향이 없습니다.
